# 仕入れリサーチツール（sedori/）の詳しい説明

CLAUDE.md の「仕入れリサーチツール」の節から移した詳しい説明です（2026-11-28、利用者の依頼で CLAUDE.md を短くするため。内容は消さずに移しました）。大事なルールは CLAUDE.md の上に残してあります。資料の反映記録は `SOURCES.md`。

## 仕組み・方針・決まり

クイズアプリとは独立した別ツール。Amazon 物販の仕入れ候補を絞り込む静的ページ（`sedori/index.html` / `style.css` / `app.js`、外部依存なし）。

- Keepa の Product Finder から書き出した CSV を読み込み、月の販売数・出品者数・価格などで絞り込む。列名は英語/日本語の両方を `FIELDS` のパターンで自動判定し、画面上で手動の割り当て変更も可能。
- 「仕入れ上限」= 販売価格 − 販売手数料 − FBA手数料 − 小口出品の基本成約料（`smallFee`、初期値100円。利用者の指示で大口出品に切り替えるまで入れる。手数料 `it.fees` に含む）− その他経費 − 欲しい利益。
- 実際の Keepa 日本語エクスポート（167 列。`商品名` / `Buy Box: 現在` / `新品: 現在` / `Buy Box: 90 日平均` / `月間売上トレンド: 先月の購入` / `新品アイテム数: 現在` / `FBA Pick&Pack 料金` / `紹介料％` / `商品コード: EAN` など）で列の自動判定を確認済み。`Buy Box: 現在` は空欄が多いため `新品: 現在` で補い、計算用の販売価格は「いまの価格」と「90 日平均」の低いほうを使う。`Amazon: 現在` も空欄が多いため、`Buy Box: % Amazon 90 日` が 30% 以上なら Amazon 本体ありとみなす。型式欄は検索に使えない値が多く、`usableModel()` で選別する。
- リサーチの手法を切り替えられる（`app.js` の `MODES` と `EVAL`）: 通常／値上がり／トレンド／刈り取り／即刈り／セラー／クーポン。手法ごとに条件の初期値（`params`）、計算に使う販売価格、商品名の下に出す見どころ（`it.lines`）、並び順の点数（`it.score`）が変わる。条件の初期値と「Keepaに入れる検索条件」は利用者のドライブの資料（YouTube 文字起こし）に合わせた。クーポンだけは資料に具体的な条件が無く、一般的な考え方で作った。手法ごとの条件は `settings.modeParams[手法キー]` に保存。
- 値上がり率は Keepa の「下落％」列の符号を逆にして使い、列が無ければ「新品: 現在」と期間平均から計算する。手法に必要な列がファイルに無いときは `#mode-warn` に案内を出す（必須の列が無ければ 0 件、補助の列が無ければその条件だけ外す）。**下落％・在庫切れ率(OOS)・ランキング・クーポンの日本語の列名は推測で、実際の Keepa ファイルでは未確認**（違っていたら `FIELDS` のパターンを直す。画面の「列の割り当て」でも選べる）。
- どの手法でも共通: 出品者の数が 30 日平均から 3 割以上かつ 2 人以上増減したら注意書きを出す（`sellerTrend()`）。「出品者が増えている商品を除く」（初期値オン）と「月の販売数が分からない商品も表示する」（初期値オフ）の設定あり。根拠は合宿スライド 4 コマ目。「自己配送で売る場合の仕入れ上限も表示する」（初期値オフ、送料の初期値 200 円）をオンにすると、FBA 手数料の代わりに送料で計算した `it.limitSelf` を出し、FBA では赤字でも自己配送で利益が残る商品も残す。根拠はリベ大「自己配送 始め方 マニュアル」。どの手法でも「月の販売数 ÷ 出品者数 ＝ 1人あたり月に売れる個数」と、`新品: 最低`（列名は推測、`lowNew`）があれば「過去最低価格まで下がっても赤字にならない仕入れ値」（`it.limitAtLow`）を表示する。根拠は合宿スライド 2 コマ目。「Amazon本体がよく販売している商品を除く」は通常とセラーの手法で効く（`.basic-seller`、リベ大「せどり相談室」）。
- **資料からの更新**: 利用者はドライブの「せどり資料」フォルダに資料を追加していき、それに合わせてツールを更新する方針（毎日の定期作業あり）。どのファイルを読んで何を反映したかは `sedori/SOURCES.md` に記録する。新しい資料を反映するときは、まずこの表に無いファイル・更新日時が新しいファイルだけを読み、反映後に表へ追記する。資料に根拠のない数字や手法は足さない。**リベ大（リベシティ）の資料を最優先**にし、ほかの資料と食い違うときはリベ大に合わせる（見分け方は SOURCES.md）。ドライブの「09_Claude活用」フォルダは Claude の使い方の資料置き場で、ツールは書き換えずに活用方法の提案として報告する（詳細は SOURCES.md）。作業用ブランチは `claude/focused-hamilton-vmvpmn`、正式な場所（既定ブランチ）は `claude/understand-project-purpose-UDFWc`。利用者の依頼（2026-11-22）により、毎朝の定期作業で変更があり確認（`node --check` と画面の動作確認）が通った日は、プルリクエストを作って正式な場所へマージまで行う。確認に失敗した日はマージせず報告する。
- 「5. ポイント・クーポン込みの仕入れ値を計算」（`calc()` / `openCalc()`）: 表示価格・送料・クーポン（円 or %、上限）・ポイント率から、もらえるポイント＝（表示価格÷1.1−クーポン）×率（切り捨て）、実質仕入れ値＝表示価格＋送料−クーポン−ポイント、見込み利益＝売価−手数料−実質仕入れ値、損益分岐＝実質仕入れ値＋手数料を出す。式はリベ大 合宿プロンプト集（2コマ目「リサーチ補助」）のとおりで、計算例（39,182円→実質26,905円・利益3,021円）と一致を確認済み。各商品の「ポイント込みで計算」で売価と手数料を引き継ぐ。
- 各行に Google（型式で検索）・楽天・Yahoo!・ヨドバシ・ビックカメラ・Googleショッピング・価格.com・Keepa へのリンクボタンを表示（ヨドバシ以降は仕入れ先探し用、2026-11-26 追加）。「4. 候補の商品」に「新しいお店で買う前のチェック」（支払い方法・特商法の表記・極端な安さ・見た目。銀行振込だけは要注意。一般的な考え方）を表示し、確かめた結果はスプレッドシート「仕入れ」タブの Z列「仕入れ先の確認」に利用者がメモする。Claude が知らないお店のサイトを自動で見て回ることはしない（ネットワークの許可範囲と規約のため）。
- 楽天/Yahoo! の最安値取得は、利用者が画面で入力した ID を使ってブラウザから直接問い合わせる。ID は localStorage（`sedori-research-settings-v1`）にのみ保存し、**リポジトリには絶対に書かない**。実際の ID での動作は未確認（Yahoo! はブラウザから直接つなげない可能性あり）。
- 出品チェック: 商品(ASIN)ごとに「出品できる/申請で通った/書類が必要/不可」を記録し、メーカー別に集計する。保存先は localStorage（`sedori-listing-checks-v1`）。JSON ファイルでのバックアップ/復元あり（復元は既存の記録を上書きせず追加のみ）。
- **スマホ（iPhone）操作が前提**。幅 760px 以下では表をカード表示に切り替える。ボタンは 44px 以上の高さを保つ。
- 利益管理（`sedori/kanri.html` / `kanri.js`、`style.css` は共用）: 仕入れ（1回の購入単位）と、それに結びつく売上を記録し、利益・在庫を集計する。保存先は localStorage（`sedori-ledger-v1`、`{ purchases: [...], sales: [...] }`）。1個あたり仕入れ額 = 仕入れ値 + 経費合計 ÷ 個数。CSV 書き出し（確定申告の元資料用）と JSON バックアップ/復元（復元は全置き換え、確認あり）。リサーチ画面の「仕入れを記録」は `kanri.html?add=1&...` で商品情報を引き継ぐ。Amazon の売上ファイル取り込みは未実装。在庫が残っている仕入れには、仕入れからの日数に応じて値下げ・損切りの目安を出し（`agingAdvice()`、30日〜−10%、60日〜−20%、90日〜一部損切り、150日〜処分。リベ大「せどり相談室」）、まとめに「3か月以上売れ残り」を出す（リベ大「せどりの資金管理術」）。
- **利益管理の記録はスプレッドシートへ移行（2026-11-23、利用者の依頼）**: PC とスマホの両方で同じ記録を使うため、記録の正式な置き場所は利用者の Google ドライブ「せどり記録」フォルダのスプレッドシート「せどり 利益管理」（タブ: まとめ／仕入れ／売上／値下げの目安／使い方）。仕入れは「仕入れ番号」（P001…）で売上と結びつき、売れた個数・残り個数・値下げの目安・損益分岐（W列＝1個あたり仕入れ額＋予定の手数料）・SKUの例（X列）は数式で自動計算。SKU は利用者の決定（2026-11-24）でリベ大のおすすめ「仕入れ値_仕入れ日(yyyymmdd)_損益分岐」にする（仕入れ番号は入れない）。売上ファイルを取り込むときは、SKU の仕入れ日・仕入れ値と ASIN から仕入れの行を探して仕入れ番号を決める。Claude が書き込むのは黄色の入力列だけ。記録の中身はリポジトリに書かない（スプレッドシートのアドレスは利用者の了承済みで `app.js` の `LEDGER_URL` に置く。中身は本人しか開けない）。リサーチ画面の「仕入れを記録」と上部の「利益管理」はこのスプレッドシートを開き、「仕入れを記録」は商品名・メーカー・ASIN・JAN をタブ区切りでコピーする。`kanri.html` は端末ごとの保存のまま残し、移行の案内を出している。店舗仕入れのレシート写真は「せどり記録」内の「仕入れレシート」フォルダに入れてもらい、毎朝の定期作業で読んで「仕入れ」タブに書き込む（記録元の列にファイル名を書き、二重に書き込まない）。
- **トラッキング候補（2026-11-24、利用者の依頼。進め方A＝Claude が選び、利用者が Keepa で設定）**: 利用者が週1回、Keepa Product Finder（「刈り取り」の検索条件）の CSV をドライブ「せどり記録」→「Keepaファイル」フォルダに入れる。毎朝の定期作業で新しいファイルがあれば、`node sedori/tools/tracking-candidates.js <CSV>`（`python3 -m http.server 8765` を先に起動。画面と同じ計算をブラウザで実行して「刈り取り」の結果を JSON で出す）で候補を出し、スプレッドシートの「トラッキング候補」タブに書き込む（目標価格＝Keepaで「Amazonが ○円以下」の金額、元のファイル名を記録して二重に書かない）。Keepa への設定操作は Claude はしない（Keepa のアカウントや API につながっていない）。
- **規制解除の候補ブランド（2026-11-26、利用者の依頼）**: 利用者のアカウントはまだ育っておらず、ほぼ全ブランドに出品規制がある。Amazon以外で同じブランドを（多くは10個以上）仕入れた領収書で解除する前提で、画面の「7. 規制解除の候補ブランド」（`unlockBrands()` / `renderUnlock()`）が「4. 候補の商品」の結果をブランドごとにまとめ、条件に合った商品が多いブランドから並べる。解除用の商品は「必要な個数（`unlockQty`、初期値10）を、自分も出品者に加わる前提で3か月以内に売り切れる」商品のうち費用（仕入れ上限×個数）が最小のもの（1か月以内を優先、出品者1人の商品は除外、予算 `unlockBudget` で上限）。出品チェックで「出品できる／申請で通った」があるブランドは外す。根拠はリベ大 合宿（1か月で売り切れる数・遅くとも3か月）と「出品規制解除の方法を1から完全解説」。
- **方針: くり返し仕入れ（2026-11-26、利用者の決定）**: 一時的な値下がりの刈り取りより、いつも安い仕入れ先がある商品を Amazon の在庫が減るたびに補充する形を目指す。手法「リピート向き」（`repeat`）は、販売価格＝いまと90日平均の低いほう、月の販売数（初期値50）、30日・90日の値動きが一定以内（初期値15％。資料の数字ではなく PRICE_SPIKE に合わせた目安）、出品者が増えていない、Amazon本体があまり売っていない商品を残し、「自分が加わったときの1人あたり月販」で並べる。規制解除の候補ブランドは、表示中の手法に関係なく「リピート向き」の結果で並べる（利用者の希望で当面優先）。スプレッドシート「仕入れ」タブの Y列「仕入れ先のURL（補充用）」は利用者の入力欄で、毎朝の報告で残りが少ない商品を「補充どき」として知らせる。
- **参考セラー（2026-11-26、利用者の依頼）**: リベ大 じゅんKさんの「セラーリサーチ」（手法「セラー」）を週1回の流れに組み込んだ。利用者が出品数100件前後の個人の出品者をスプレッドシート「参考セラー」タブに記録し、Keepa 製品ファインダーの「販売者ID」で書き出した CSV を `seller_<ID>.csv` の名前で「Keepaファイル」に入れる。毎朝の定期作業で `research.js` の「セラー」「リピート向き」の結果を仕入れ候補に足し、`sellerBrands`（セラーの結果に多いブランド）を参考セラーの G列に書く。Amazon のページを Claude が自動で巡回することはしない（出品者を選ぶのは利用者）。`render()` は各行に `data-brand` を付ける（補助スクリプト用）。
- **バリエーション（2026-11-26、利用者の依頼）**: FIELDS に `parent`（親ASIN）・`reviews`（レビュー数）・`color`・`size` を追加（**日本語の列名は推測、実ファイルで未確認**）。`buildItems()` の後で `applyVariations()` が親ASINごとにまとめ、同じシリーズの「月の販売数」がすべて同じならシリーズ全体の数とみなしてレビュー数の割合で各商品に分ける（リベ大 合宿2025-08 2コマ目「シリーズ全体の販売数 × レビューの割合」）。レビュー数が無ければ注意書きだけ出す。候補に同じシリーズの別の色・サイズが残れば知らせ、規制解除の候補ブランドはシリーズ単位で数える。週1回の書き出しと手法「リピート向き」は、色・サイズ違いも含めるため「1製品につき1バリエーション」のチェックを外す（`VARIATION_ALL_TIP`）。
- **ロードマップと担当の分担（2026-11-26）**: 利用者は Claude の担当を分けている（戦略担当／実務担当＝このリポジトリの毎日の作業とツール作り／財務・経理担当（全事業））。方針は「せどり事業 ロードマップ」（せどり記録フォルダ。1年後に月利50万円）、担当の全体は「担当一覧（全事業）」（事業の共通フォルダ）。「せどり 利益管理」は実務担当が受け持ち、財務・経理担当は読むだけ。各担当は自分の文書にだけ書き、実務担当の共有先はドライブ「せどり記録」の文書「実務担当からの共有（せどり）」（新しいものを上に書く）。毎朝、ほかの担当の文書を読み、関係することは利用者に確かめてから動く。ロードマップの依頼で、スプレッドシートに「月次まとめ」（第1段階のチェック、月ごとの売上・月利・利益率・仕入れ額・在庫・現金・補充できる商品・規制解除の数。月末の在庫などは毎月はじめに実務担当が記録）と「リピート向きの集計」タブを作り、`research.js` が `repeatByCategory` / `repeatByBrand` を出す。画面に「化粧品など女性向けの商品を除く」（`noWomen`、初期値オン、`isWomenItem()` はカテゴリーと商品名の言葉で判断）を追加。
- **ポイントの扱い（2026-11-26、利用者の決定）**: 利益（月利）には仕入れでもらったポイントを含めない（実際のお金の出入りに合わせる）。スプレッドシート「仕入れ」タブ AA列「もらったポイント（その仕入れ全体の円分）」に記録し、「月次まとめ」の M列（その月の仕入れでもらったポイント）・N列（ポイント込みの実質利益（参考））に別に出す。リサーチツールの「仕入れ上限」はポイントを含まず、「5. ポイント・クーポン込みの仕入れ値を計算」だけがポイントを引く。税金での扱いは財務・経理担当が確認中。
- **入金と保留（2026-11-26、利用者の依頼）**: 利益（月利）は売れた日で数え、Amazon の入金が保留になっても利益は変わらず、手元のお金が入るのが遅れるだけ。スプレッドシート「売上」タブに N列「入金の状況」（入金待ち／保留中／入金済み。空欄は入金待ち扱い）・O列「入金予定日」・P列「保留の理由・メモ」・Q列「注文番号」（以上は入力欄）と R列「入金される金額（売上−手数料）」（数式）を足し、「月次まとめ」の O13「入金待ちの金額（保留中を含む）」・P13「うち保留中の金額」に出す。2026-11-26 に、つながる Gmail をセラー用のアドレスに統一した。毎朝、Amazon からの送金・保留・未払い残高の請求・出品許可のメールを読む（送金のメールからはどの売上が含まれるか分からないので、行を勝手に「入金済み」にしない。出品許可のメールは送り主のつづりを確かめ、怪しければセラーセントラルで確認してもらう。パスワードなどアカウントの安全に関わるメールは開かない）。資金繰りは財務・経理担当の受け持ちなので共有する。
